# CODEX AUDIT — Call log must center on tokens/sec, cost, and actionable failures

Date: 2026-09-17  
Role: Codex auditor/mentor. DeepSeek owns product code changes.

## Verdict

Current call log / usage view is not SOTA yet.

The important per-call signal for an LLM router is not a table full of raw milliseconds. The operator and developer need to know:

- how many tokens went in/out;
- how fast the model/provider moved tokens;
- how much the call cost;
- whether the router overhead stayed tiny;
- which provider/model/team/key caused errors.

Raw `228453ms` in a main table without context is noise. It should be formatted and moved into a detail/diagnostic column, while token throughput becomes first-class.

## Current state observed

`usage_ledger` already has useful base fields:

- `input_tokens`
- `output_tokens`
- `estimated`
- `ttfb_ms`
- `total_ms`
- `router_overhead_ms`
- `stream`
- `client_aborted`
- `error_class`

Portal currently displays logs with columns similar to:

- Time
- Team
- Key
- Model
- Status
- Input
- Output
- TTFB
- Total
- Request ID

This is too raw. It hides the signal users care about: token throughput.

## Definitions to use consistently

Add a small legend in docs and UI tooltips. Do not use unexplained jargon.

- Input tokens: prompt/context tokens sent to the provider.
- Output tokens: answer tokens generated by the provider.
- Total tokens: input + output.
- Time to first byte: how long until the first response byte arrives.
- Router overhead: time spent inside BrighTO-Router before forwarding to provider.
- Total time: full request duration from router receive to response completion.
- Tokens per second: observed token throughput for this call.

Use `tok/s` only after the UI has explained once that it means “tokens per second”.

## What to compute per call

Do not add columns unless needed for query performance. These can be computed from existing ledger fields and route prices.

### Required computed fields

For each usage row returned by admin/user usage API, include:

```json
{
  "input_tokens": 200058,
  "output_tokens": 8,
  "total_tokens": 200066,
  "total_seconds": 228.453,
  "time_to_first_byte_seconds": 228.1,
  "router_overhead_ms": 3,
  "total_tokens_per_second": 875.8,
  "output_tokens_per_second": null,
  "input_tokens_per_second_to_first_byte": 877.0,
  "prompt_size_bucket": "128k+",
  "estimated_cost_usd": 0.0,
  "tokens_estimated": false
}
```

### Formula rules

- `total_tokens = input_tokens + output_tokens`
- `total_seconds = total_ms / 1000`
- `total_tokens_per_second = total_tokens / total_seconds` when `total_ms > 0`
- `input_tokens_per_second_to_first_byte = input_tokens / (ttfb_ms / 1000)` when `ttfb_ms > 0`
- `output_tokens_per_second = output_tokens / ((total_ms - ttfb_ms) / 1000)` only when `total_ms > ttfb_ms` and output tokens are known

If the formula is not reliable, return `null` and label it clearly. Do not invent precision.

### Streaming vs non-streaming caution

For streaming responses, `ttfb_ms` is close to first token / first event time, so separating prompt prefill and generation throughput is useful.

For non-streaming responses, many providers send headers only when the whole answer is ready. In that case `output_tokens_per_second` may be unknown. Use `total_tokens_per_second` and mark output tok/s as `null` if the split is not valid.

## Prompt size buckets

Every usage row and performance summary should include a bucket derived from input tokens:

- `<2k`
- `2k–32k`
- `32k–128k`
- `128k+`

This prevents a 200k prompt from polluting the apparent latency of normal 1k chat calls.

## Cost calculation

For each row, calculate estimated cost from route prices when available:

```text
cost = input_tokens * price_input_per_mtok_usd / 1,000,000
     + output_tokens * price_output_per_mtok_usd / 1,000,000
```

If prices are missing:

- return `estimated_cost_usd: null`;
- UI shows `—`, not `$0`, unless price is explicitly configured as zero.

Dashboard cost should aggregate only rows with known prices and show a note if some rows have missing prices.

## Admin call-log table

Replace the current raw table with this default column order:

1. Time
2. Team
3. Key
4. Public model
5. Provider
6. Status
7. Tokens in/out
8. Tok/s
9. Cost
10. Router overhead
11. Duration
12. Error

Recommended display:

| Column | Example | Rule |
|---|---|---|
| Tokens in/out | `200,058 / 8` | Always visible. |
| Tok/s | `876 total tok/s` | Prefer total tok/s; show output tok/s only when reliable. |
| Cost | `$0.0142` or `—` | Use route prices; `—` when unknown. |
| Router overhead | `3 ms` | This is the key router performance number. |
| Duration | `3m 48s` | Friendly format, not raw `228453ms`. |
| Error | `timeout`, `429`, `provider_5xx` | Empty for success. |

Request ID should be copyable but not consume a wide default column. Put it in a details drawer or last compact column.

## User call-log table

User view should be simpler:

1. Time
2. Model
3. Status
4. Tokens in/out
5. Tok/s
6. Cost
7. Duration
8. Error

Do not show all teams, all keys, provider credentials, or admin-only route details.

## Dashboard cards

Top dashboard cards should not show global provider total latency.

Use:

- Requests today
- Tokens today
- Estimated cost today
- Error rate today
- Active routes
- Router overhead p95

If showing speed, use:

- Median tok/s by model/provider for recent successful calls
- Slowest models by tok/s
- Provider error rate

Do not show `P95 total` globally across all prompt sizes.

## Performance diagnostics section

A separate section/page can show deeper timing:

- router overhead p50/p95/p99;
- first-byte latency by provider/model/prompt bucket;
- total duration by provider/model/prompt bucket;
- total tok/s by provider/model/prompt bucket;
- output tok/s where reliable;
- slowest 20 calls.

This section is for diagnosing providers and local GPUs/CPUs, not for the main business dashboard.

## Operational logging policy

Runtime logs should be quiet by default.

### Keep these logs

- startup config: protocol, listen addr, version;
- config reload failure/stale warnings;
- ledger fallback enter/exit;
- provider health transition: healthy -> unhealthy, unhealthy -> healthy;
- request failure summary at warn/error level;
- optional sampled slow-call log when duration or router overhead exceeds threshold.

### Remove or avoid these logs

- successful config reload every 5 seconds;
- successful health poll every 5 seconds;
- boot counter from usage ledger on every config reload;
- full request/response bodies;
- provider keys, BrighTO keys, Authorization headers;
- raw SQL spam;
- per-chunk stream logs;
- unbounded per-request info logs for every successful call.

Usage ledger is the per-call source of truth. Runtime logs are for operators when something is wrong.

## Slow-call logging

Add a single structured warning only when useful:

```json
{
  "event": "slow_llm_call",
  "request_id": "...",
  "team_id": 12,
  "key_prefix": "lc-1234abcd",
  "model": "qwen-local",
  "provider": "local-llama",
  "status": 200,
  "input_tokens": 200058,
  "output_tokens": 8,
  "total_ms": 228453,
  "router_overhead_ms": 3,
  "total_tok_s": 875.8,
  "prompt_bucket": "128k+"
}
```

Default thresholds:

- log when `router_overhead_ms > 50ms` because router should be tiny;
- log when `status >= 400`;
- optionally log when `total_ms > 60s` but only with prompt bucket and tok/s, so long context is not mistaken for router slowness.

## API changes required

Extend `/admin/usage` and `/portal/me/usage` responses with computed fields:

- `total_tokens`
- `total_seconds`
- `ttfb_seconds`
- `duration_display`
- `router_overhead_display`
- `total_tokens_per_second`
- `input_tokens_per_second_to_first_byte`
- `output_tokens_per_second`
- `prompt_size_bucket`
- `estimated_cost_usd`
- `cost_known`

Keep old raw fields for compatibility, but UI should not lead with raw ms.

Extend `/admin/summary` or add `/admin/performance` with grouped throughput:

- by model;
- by provider/backend;
- by team;
- by prompt size bucket;
- success/error split.

Keep SQL simple. Use aggregates over recent time windows with existing indexes. Add indexes only after measuring slow queries.

## Concrete UI target

A successful local llama 200k row should look roughly like:

```text
04:20  local-llama-audit  qwen3.8-flash-next  200  200,058 / 8 tok  876 total tok/s  $0.00  router 3 ms  3m 48s
```

This is readable and actionable. It tells the admin the model handled a 200k prompt at about 876 total tokens/sec while router overhead was only 3ms.

The current `228453ms` display does not tell that story.
